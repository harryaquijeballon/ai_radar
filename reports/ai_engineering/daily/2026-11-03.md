## Today's developments

### 1. When Neither Side Confirms: Destructive Tool Approval Across MCP Servers and Hosts (academic, Junwei Yao, Zike Yang, Zhijun Wang, Yongxi Zhou, Wenbo Ye, 2026-11-02)

**Why it matters:** A large source-code study (1,000 MCP registry
repositories, 41 hosts/SDKs) finding that about 90% of destructive MCP
tools have no server-side confirmation and 60.7% of tool/application pairs
have no enforced default human approval; low-cost models executed an
injected deletion in half of live-test runs. The paper's own simulated
fix — deny-by-default for anything not explicitly marked safe — cuts the
unapproved share to 5.4%, a concrete configuration change for anyone
deploying MCP-based agents with write/delete-capable tools.

**Source:** https://arxiv.org/abs/2611.02527 · **Library entry:** [2026-yao-destructive-tool-approval-mcp](../../../library/entries/2026-yao-destructive-tool-approval-mcp.md)
**Selected because:** High on tool use and MCP (lens 3) and reproducibility/security/governance (lens 6) — a severe, quantified, ecosystem-wide gap with a measured mitigation, not a single-incident report.

### 2. Built on Broken Assumptions (BOBA): Why Coding Agents Cannot Be Left Alone (academic, Alejandro Cuadron, Arpit Gupta, 2026-11-01)

**Why it matters:** A new 280-chain, 140-repository benchmark shows ten
coding agents complete ~95% of isolated requests but only 51% of
20-request chains — not because of worse code, but because agents trust
their own (incomplete) tests and rarely catch their own mistakes later
(~53% self-correctness-detection accuracy). One external verification
signal plus a repair round raises chain completion to 59%. Directly
transferable to any agentic coding pipeline currently relying on an
agent's self-reported "done."

**Source:** https://arxiv.org/abs/2611.02207 · **Library entry:** [2026-cuadron-gupta-boba-coding-agent-chains](../../../library/entries/2026-cuadron-gupta-boba-coding-agent-chains.md)
**Selected because:** High on evaluation/validation/deterministic guardrails (lens 4) — isolated-task benchmarks don't predict multi-step chain reliability, with a named cause and a measured fix.

### 3. Same Text, Different Filename: Are LLM Judges Biased? (academic, Sergey V. Popov, 2026-11-01)

**Why it matters:** Three frontier LLMs scored an identical document
differently depending only on its filename's label, with a
context-specific (not simply predictable) bias. A concrete, named failure
mode for any pipeline using an LLM as a judge or quality gate — blind,
metadata-stripped evaluation should be the default wherever an LLM judge
gates a decision.

**Source:** https://arxiv.org/abs/2611.01829 · **Library entry:** [2026-popov-llm-judges-filename-label-bias](../../../library/entries/2026-popov-llm-judges-filename-label-bias.md)
**Selected because:** High on evaluation, validation and deterministic guardrails (lens 4) — a specific, testable LLM-as-judge failure mode with a stated real-world stake (journals already using such tools).
